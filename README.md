1. Суть проекта
По сути, это аналог Stepik или Coursera. Веб-приложение, где преподаватели собирают курсы с уроками и тестами, а студенты изучают материал, выполняют практические задания, общаются с авторами и получают итоговые сертификаты.
Функционал, выходящий за рамки стандартного учебного CRUD:
•	Видеосвязь прямо в браузере (WebRTC): индивидуальные онлайн-консультации без зума и сторонних сервисов.
•	Чат в реальном времени (Socket.io): переписка со студентами с поддержкой статуса «в сети».
•	Автоответчик для поддержки: если преподаватель офлайн, базовый бот перехватывает типовые вопросы по платформе.
•	Сборка PDF-диплома на лету: генерация именного файла с уникальным ID и кодом валидации.
•	Авторизация через Google: быстрый вход через аккаунт Google без ввода пароля.
2. Путь запроса: от клика в браузере до базы
Посмотрим на примере открытия каталога курсов:
[Браузер / React] 
       ↓ (GET /api/courses через axios)
[Express Router] 
       ↓ (auth middleware — если роут закрыт)
[Course Controller] 
       ↓ (вызов метода сервиса / модели)
[Mongoose] 
       ↓ (BSON-запрос)
[MongoDB]
1.	Пользователь заходит на страницу /courses. Срабатывает хук (например, useEffect), дергая клиент axios.
2.	Запрос уходит на GET http://localhost:5000/api/courses. Если в localStorage лежит JWT, интерцептор axios подшивает его в заголовок Authorization: Bearer <token>.
3.	Express принимает запрос, прогоняет через глобальные мидлвары (CORS, Helmet, Rate Limiter) и отдает в нужный роут (routes/courses.js).
4.	Роут перенаправляет вызов в контроллер (controllers/courseController.js).
5.	Контроллер обращается к Mongoose-модели: Course.find({ isPublished: true }).
6.	Mongoose забирает документы из MongoDB и парсит их в JSON.
7.	Ответ поднимается обратно: MongoDB -> Mongoose -> Контроллер -> Express -> Браузер.
8.	React ловит JSON и сохраняет его в стейт, вызывая рендер карточек курсов.
3. Архитектура папок
Проект разделен на две независимые части — client и server:
plathorm_lessons/

│   └── src/
│       ├── components/         # Кнопки, модалки, плеер, форма чата

│       ├── context/            # Глобальный стейт авторизации (AuthContext)
│       ├── services/           # Настроенный инстанс axios и методы API
│       └── hooks/              # Кастомные хуки (тема, сокеты)
│
└── server/                     # Серверная часть (Node.js + Express)
    └── src/
        ├── config/             # Подключение к Mongo, стратегии Passport
        ├── models/             # Схемы Mongoose (User, Course, Test и т.д.)
        ├── controllers/        # Прием запросов, валидация входных данных, ответ

4. Связка React и Express
Общение идет исключительно по REST API (JSON) + веб-сокетам. Бэкенд не генерирует HTML (серверного рендеринга нет), отдавая только сырые данные.
На клиенте настроен перехватчик (interceptor) в client/src/services/api.js:
JavaScript
const api = axios.create({
  baseURL: process.env.REACT_APP_API_URL || 'http://localhost:5000/api',
});

// Автоматически подставляем актуальный JWT во все запросы
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});
Когда юзер логинится, бэкенд возвращает токен. Фронт кладет его в localStorage, обновляет AuthContext и пушит пользователя на дашборд. Если токен протух или невалиден, API отвечает кодом 401, интерцептор ловит этот статус, чистит хранилище и перебрасывает на страницу логина.

6. Авторизация через JWT
Сессии в базе не хранятся — авторизация полностью stateless.
1.	Юзер вводит логин и пароль.
2.	Сервер находит пользователя, проверяет хеш пароля с помощью bcrypt.compare.
3.	Если все совпало, собирается токен с помощью jwt.sign: внутри зашит id пользователя и срок жизни (30 дней).
4.	Сервер отдает токен клиенту, клиент сохраняет его в localStorage.
5.	При запросе к закрытым роутам токен передается в заголовке Authorization: Bearer <token>.
6.	Мидлвар protect валидирует подпись токена (jwt.verify). Если ключ валиден, достаем пользователя из базы и кладем в req.user.
JavaScript
// middleware/auth.js
exports.protect = async (req, res, next) => {
  let token;
  if (req.headers.authorization && req.headers.authorization.startsWith('Bearer')) {
    token = req.headers.authorization.split(' ')[1];
  }

  if (!token) {
    return res.status(401).json({ success: false, message: 'Необходима авторизация' });
  }

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    const currentUser = await User.findById(decoded.id);
    
    if (!currentUser || !currentUser.isActive) {
      return res.status(401).json({ success: false, message: 'Пользователь не найден или заблокирован' });
    }

    // Проверяем, не менялся ли пароль после выдачи этого токена
    if (currentUser.changedPasswordAfter(decoded.iat)) {
      return res.status(401).json({ success: false, message: 'Пароль был изменен. Войдите заново' });
    }

    req.user = currentUser;
    next();
  } catch (err) {
    return res.status(401).json({ success: false, message: 'Недействительный токен' });
  }
};
7. Почему именно MERN
•	Один язык по всему стеку: JavaScript в клиенте и на сервере. Не приходится переключать контекст между синтаксисом бэкенда и фронтенда, а валидацию или утилитарные типы/форматтеры можно частично шарить.
•	Гибкость связки React + Express: React дает компонентный подход и реактивный UI, а Express — минималистичный каркас без лишней магии, где каждый шаг обработки запроса понятен.
•	Формат данных: И бэкенд, и клиент, и MongoDB «из коробки» общаются на языке JSON. Нет нужды мапить реляционные таблицы в объекты и обратно через тяжелые ORM.
8. Почему MongoDB, а не SQL
Курс в онлайн-школе — это сложная древовидная структура: у курса есть разделы, внутри разделов — уроки, у уроков — задания и ссылки на материалы, плюс привязанные отзывы и списки студентов.
•	В PostgreSQL под такую структуру пришлось бы поднимать 6-8 таблиц, настраивать каскадные удаления и собирать данные через массивные LEFT JOIN.
•	В MongoDB документ курса хранится в удобном виде: метаданные, массив программы (curriculum), настройки сертификата и вложенные поддокументы лежат компактно.
•	Чтение курса для отображения страницы происходит за одно точечное обращение по _id, что дает отличную скорость.
•	При добавлении новых полей в урок (например, ссылки на скачивание или флага автопроверки) не нужно писать миграции для изменения схемы таблицы.
9. Роли пользователей
В системе предусмотрено 3 роли:
•	Студент (student): базовая роль при регистрации. Может записываться на открытые курсы, просматривать материалы, отправлять ответы на тесты, общаться в чатах и скачивать свои сертификаты.
•	Преподаватель (teacher): имеет доступ к панели создания курсов, загрузке уроков, редактированию вопросов квизов, ручной проверке эссе и настройке оформления дипломов.
•	Администратор (admin): глобальный доступ. Модерирует созданные курсы, переключает флаги блокировки пользователей (isActive), назначает роли.
Ограничение по ролям работает через отдельный мидлвар authorize:
JavaScript
exports.authorize = (...roles) => {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({ success: false, message: 'Недостаточно прав для этого действия' });
    }
    next();
  };
};

// Пример использования:
router.post('/courses', protect, authorize('teacher', 'admin'), courseController.createCourse);
10. Схема базы данных
Основные коллекции и их поля:
•	users: _id, email, password (хеш bcrypt, select: false), firstName, lastName, role, provider (local/google), googleId, isActive, passwordChangedAt.
•	courses: _id, title, description, instructorId (ref -> User), price, category, level, isPublished, curriculum (массив разделов и уроков), studentsEnrolled (массив { userId, progress, status }).
•	lessons: _id, courseId (ref -> Course), title, type (video, text, quiz), content, order, duration, quizId.
•	quizzes: _id, lessonId, title, passingScore, questions (массив ID вопросов).
•	questions: _id, quizId, text, type (single, multiple, essay), options, correctAnswer, points.
•	tests (попытки сдачи): _id, studentId, quizId, courseId, status, answers (ответы юзера, флаг правильности, начисленные баллы), score, passed.
•	certificates: _id, userId, courseId, courseTitle, userName, filePath, verificationCode, issueDate.
•	messages: _id, senderId, receiverId, content, isFromAI, createdAt.
•	subscriptions: _id, studentId, teacherId, status, expiresAt.
11. Связи между коллекциями
Несмотря на документную структуру, сущности связаны между собой ссылками (ObjectId + ref):
1.	Преподаватель -> Курсы (1:N): В документе Course хранится поле instructorId, ссылающееся на User.
2.	Курс -> Уроки (1:N): Модель Lesson ссылается на courseId. Дополнительно порядок уроков фиксируется в массиве curriculum модели курса.
3.	Студенты <-> Курсы (M:N): Реализовано гибридно. В документе курса хранится массив studentsEnrolled с ID студентов и их текущим прогрессом (удобно быстро считать количество учащихся и процент прохождения).
4.	Урок -> Квиз (1:1): Поле quizId в уроке связывает его с тестом для закрепления материала.
5.	Тест -> Студент (N:1): Каждая попытка прохождения фиксируется отдельным документом Test с привязкой к studentId.
Для склейки данных на чтении используется Mongoose-метод .populate(). Например, при открытии курса автоматически подтягиваются данные об инструкторе (имя, фамилия, аватар).
12. Реалтайм-чат на Socket.io
Для мгновенного обмена сообщениями без спама запросами (polling) развернут WebSocket-сервер на базе Socket.io.
Логика на сервере:
1.	При коннекте клиент шлет событие register со своим userId. Сервер мапит userId -> socket.id и помещает сокет в персональную комнату с именем пользователя: socket.join(String(userId)).
2.	Когда юзер шлет sendMessage, сообщение сохраняется в коллекцию Message.
3.	Сервер пушит его двум адресатам: отправителю (для подтверждения) и получателю через комнату:
JavaScript
io.to(String(receiverId)).emit('newMessage', message);
4.	Если получателя нет в списке активных подключений, сервер запускает фоновую проверку автоответчика.
13. Бот-помощник (AI-виджет)
Чтобы студенты не ждали ответа на типовые организационные вопросы, в чат встроен быстрый автоответчик.
•	Как устроен: На текущем этапе это rule-based модуль (server/src/utils/aiResponses.js). Он парсит текст сообщения регулярными выражениями по ключевым паттернам («как оплатить», «сертификат», «доступ к уроку», «домашнее задание»).
•	Поведение: Если студент пишет преподавателю, а тот офлайн, сервер выдерживает паузу в 500 мс (имитация набора текста) и отвечает от имени системного бота с флагом isFromAI: true.
•	Почему так: Для MVP это решение работает мгновенно, не зависит от сторонних платных API и не падает из-за лимитов сети. Архитектура вынесена в отдельный сервис, поэтому подключение внешнего LLM-провайдера (OpenAI / локальной модели) сводится к замене логики в одном методе.
14. Видеозвонки через WebRTC
Видеосвязь реализована нативно через браузерный API WebRTC по схеме Peer-to-Peer (трафик видео и аудио идет напрямую между клиентами, не нагружая сервер платформы).
Роль сервера и сокетов (Signaling): Браузеры не могут связаться напрямую, пока не узнают IP-адреса и поддерживаемые кодеки друг друга. Сервер на Socket.io выступает посредником для обмена служебными данными:
1.	Инициатор создает offer (SDP-описание) и шлет его на сервер через сокет.
2.	Сервер перенаправляет оффер собеседнику.
3.	Собеседник генерирует answer, сервер передает его обратно инициатору.
4.	Параллельно клиенты обмениваются сетевыми маршрутами (ICE-кандидатами) через события ice-candidate.
5.	Как только прямое P2P-соединение (RTCPeerConnection) установлено, медиапотоки передаются напрямую.
15. Вход через Google (OAuth)
Аутентификация через Google настроена через библиотеку passport и стратегию passport-google-oauth20.
[Клик "Войти через Google"] → [Редирект на accounts.google.com]
                                       ↓ (согласие пользователя)
[Коллбэк /api/auth/google/callback] ← [Возврат authorization code]
       ↓ (обмен кода на профиль юзера)
[Поиск в Mongo по googleId или email]
       ↓
[Генерация JWT-токена и редирект на фронт с токеном]
Обработка конфликтов:
•	Если пользователь с таким googleId уже есть — сразу авторизуем.
•	Если есть пользователь с таким же email, но зарегистрированный вручную по паролю (provider: 'local'), мы не склеиваем аккаунты автоматически во избежание угона, а просим залогиниться по паролю.
•	Если пользователя нет — создаем новый профиль с флагом provider: 'google' и случайным пустым паролем.
16. Безопасность
•	Хеширование паролей: Использование bcryptjs с солью на 12 раундов. Исходные пароли нигде не логируются и не сохраняются.
•	Скрытие хеша: В схеме User у поля password прописан флаг select: false. Хеш не попадает в выборки по умолчанию и не утечет в ответе API.
•	HTTP-заголовки: Подключен helmet, убирающий маркер X-Powered-By: Express и проставляющий базовые защитные заголовки (CSP, HSTS).
•	Защита от спама и брутфорса: express-rate-limit отсекает более 100 запросов с одного IP за 15 минут на чувствительных роутах авторизации.
•	Очистка данных: Входные данные очищаются от попыток внедрения тегов и скриптов (XSS-атаки).
•	Контроль доступа к данным: На бэкенде встроены проверки на владельца ресурса (req.resource.user.toString() === req.user.id). Нельзя отредактировать чужой курс, подменив id в параметрах запроса.
17. Сценарий: как проходит регистрация
1.	Студент заполняет форму (имя, фамилия, email, пароль, выбор роли).
2.	React валидирует форму на клиенте и отправляет POST /api/auth/register.
3.	Контроллер передает данные в authService.register.
4.	Сервис проверяет, занят ли email: User.findOne({ email }).
5.	Если email свободен, инициализируется экземпляр User.
6.	Срабатывает Mongoose-хук pre('save'): пароль перехватывается и хешируется через bcrypt.hash(password, 12).
7.	Запись сохраняется в MongoDB.
8.	Генерируется JWT-токен на базе нового user._id.
9.	Клиент получает статус 201, сам токен и базовый объект профиля (без хеша пароля).
10.	Фронтенд сохраняет токен в localStorage и выполняет редирект в личный кабинет.
18. Сценарий: логин и валидация токена
1.	Форма входа отправляет POST /api/auth/login с email и password.
2.	Контроллер делает запрос к базе: User.findOne({ email }).select('+password') (принудительно запрашивая поле с хешем).
3.	Если пользователь найден, вызывается bcrypt.compare(password, user.password).
4.	При несовпадении отдается общий ответ: 401 Unauthorized: Неверный логин или пароль (не раскрывая, что именно не подошло).
5.	Если пароль верный, обновляется поле lastLoginAt, генерируется JWT и возвращается клиенту.
6.	При последующих обращениях фронтенд передает токен.
7.	Мидлвар проверяет токен и сверяет дату выдачи с датой passwordChangedAt — если после создания токена пароль сбрасывался, старый токен признается недействительным.
19. Сценарий: прохождение курса и учет прогресса
1.	Студент нажимает кнопку «Записаться» (POST /api/courses/:id/enroll). Его userId добавляется в массив studentsEnrolled курса со значением progress: 0.
2.	В интерфейсе открывается программа курса. Студент смотрит материал первого урока.
3.	По окончании урока нажимается кнопка «Завершить урок» (POST /api/courses/:id/lessons/:lessonId/complete).
4.	Бэкенд находит запись курса, фиксирует ID пройденного урока в истории прогресса студента.
5.	Сервер вычисляет долю завершенных уроков от общего количества в курсе:
progress=(всего уроковпройдено уроков)×100%
6.	Обновленный процент сохраняется в документе курса.
7.	Когда прогресс достигает 100% и сдан итоговый квиз, статус меняется на completed, и открывается доступ к генерации диплома.
20. Тесты и подсчет баллов
1.	Студент открывает квиз, прикрепленный к уроку или финальному модулю.
2.	Создается документ попытки (Test) со статусом in-progress.
3.	Студент отправляет массив выбранных ответов (POST /api/tests/:testId/submit).
4.	Сервер сопоставляет каждый ответ студента с эталоном из коллекции Question:
o	Одиночный/множественный выбор: автоматическое сравнение массивов индексов. За верный ответ начисляются баллы, прописанные в вопросе.
o	Эссе / открытый ответ: вопрос помечается флагом needsGrading: true, а тесту присваивается статус ожидания проверки преподавателем.
5.	Сервис считает суммарный процент выполнения:
percentage=(максимальные баллынабранные баллы)×100%
6.	Если набранный процент выше или равен passingScore (по умолчанию 70%), попытка помечается как passed: true.
21. Генерация PDF-сертификата
Генерация вынесена на сервер, чтобы исключить подделку верстки в браузере.
1.	Студент запрашивает выдачу сертификата (POST /api/certificates).
2.	Сервис проверяет выполнение условий: статус курса должен быть completed, а финальный тест — сдан.
3.	Задействуется библиотека pdf-lib:
o	Создается пустой PDF-документ заданного формата.
o	Накладывается векторная рамка, логотип и декоративные элементы.
o	Подключается шрифт с поддержкой кириллицы.
o	В тело документа впечатываются: ФИО студента, название курса, дата завершения, итоговый балл и уникальный номер сертификата (CERT-<timestamp>-<hash>).
4.	Дополнительно генерируется verificationCode (UUID), который сохраняется в базе вместе со ссылкой на готовый файл.
5.	Готовый бинарник сохраняется в /uploads/certificates/, а ссылка возвращается студенту.
6.	Любой работодатель может открыть эндпоинт /api/certificates/verify/:code и проверить, действительно ли выдавался такой документ.
22. С какими граблями столкнулся при разработке
•	Установка соединения в WebRTC (NAT и фаерволы): При локальной разработке все работает мгновенно. При тестировании с разных устройств видеопотоки зависали на стадии согласования. Пришлось разбираться в механике ICE-кандидатов и подключать публичные STUN-серверы Google для пробива NAT.
•	Шрифты в PDF: Стандартные шрифты pdf-lib (Helvetica, Times) не умеют отображать русские буквы (вылетали кракозябры или ошибки кодировки). Решил проблему прямой загрузкой и встраиванием кастомного TTF-шрифта с поддержкой UTF-8.
•	Инвалидация старых JWT при смене пароля: Если токен выпущен на 30 дней, а пользователь сменил скомпрометированный пароль, старый токен продолжал работать. Добавил в схему User поле passwordChangedAt и проверку временных меток в мидлвар авторизации.
•	Коллизии при авторизации через Google: Пользователи регистрировались через почту, а затем пробовали жать «Вход через Google». Пришлось продумать четкую логику проверки существующих email и запретить неявную перезапись локальных профилей.
23. Почему сначала делал бэкенд
•	Контракт взаимодействия: Пока нет четкой структуры данных и спроектированных роутов, верстать компоненты интерфейса бессмысленно — придется переписывать их под меняющийся формат ответа сервера.
•	Изолированное тестирование: Весь функционал (создание записей, проверка паролей, подсчет очков за тесты) проверялся в Postman до написания первой строчки клиентского кода. Это гарантировало, что ошибки на этапе сборки фронта связаны исключительно с UI, а не с падением базы.
•	Безопасность: Логика проверки прав должна жестко контролироваться сервером. Если начинать с фронтенда, легко попасть в ловушку, когда проверки реализуются только на кнопках в интерфейсе, оставляя дыры в API.
24. Паттерны и архитектурные решения
•	MVC + Service Layer: Логика разделена. Роуты принимают URL, контроллеры достают параметры и передают задачи сервисам. Сервисы выполняют бизнес-логику и взаимодействуют с моделями базы данных.
•	Middleware Chain: Использование цепочек промежуточных обработчиков в Express. Это позволило изолировать сквозные задачи (логирование, проверка JWT, проверка прав роли, защита от DDoS) от основной логики контроллеров.
•	Интерцепторы (Axios Interceptors): На клиенте запросы и ответы проходят через централизованные фильтры. Это избавило от необходимости вручную прописывать токен авторизации в каждом вызове.
•	Centralized Error Handling: Все ошибки отлавливаются глобальным мидлваром-обработчиком на бэкенде, приводя стек ошибок к аккуратному JSON-ответу с понятными статус-кодами.
25. Планы по масштабированию
Если проект пойдет в реальную эксплуатацию с нагрузкой, архитектуру можно масштабировать по шагам:
1.	Горизонтальное масштабирование бэкенда: Node.js-инстансы запускаются в нескольких копиях за балансировщиком Nginx. Так как JWT не привязан к памяти конкретного сервера, балансировка работает без проблем.
2.	Redis для сокетов: Для работы Socket.io на нескольких серверах подключается @socket.io/redis-adapter через механизм Pub/Sub, чтобы пользователи на разных инстансах сервера без задержек получали сообщения чата.
3.	Вынос тяжелых задач: Генерация PDF-документов и отправка писем при высокой нагрузке могут блокировать Node.js Event Loop. Их стоит вынести в отдельную очередь задач (например, BullMQ + Redis).
4.	Хранение медиафайлов: Перенос видеоуроков и сгенерированных дипломов с локального диска сервера в облачное объектное хранилище (S3-совместимое) с раздачей через CDN.
